  ### Important
  1. **register.tsx:561-568 and :570-573. A stagger timer can leave a dead entry in `activePolls`, so a refollowed team never polls.**
     - The timers set in `startPolls` are untracked. They are not in `pendingPolls`, so `stopPoll` cannot cancel them.
     - `poll` sets `activePolls[key]` at :573 before it checks that the team is still followed (:578). When the check fails it returns at :581 without clearing the key.
     - Scenario: 20 teams are followed at session start, so stagger timers run for about 9.5s. The user unfollows team 15 at t=2s, which runs `stopPoll` and deletes its key. At t=7.5s team 15's stagger timer fires and `poll` sets `activePolls[team15]` again. The check finds it unfollowed and returns, leaving the key behind.
     - The user then refollows team 15 and `syncPolls` sees `activePolls.has(key)`, so it skips `poll`. The team is followed but never polled, with no reading, until the next session.start.
     - The same orphan can occur if a stagger timer fires after any unfollow.
     - Fix: in `poll`, return before `activePolls.set` when the team is no longer followed. Alternatively delete the key when `isLatest() && !isFollowed`. Better still, track the stagger timers in `pendingPolls`.
     - No test covers this.
  2. **:553-559. `syncPolls` does not stagger, and the spec says it should.**
     - The spec says syncPolls starts loops "staggered about 500 ms apart". Only `startPolls` staggers.
     - `syncPolls` awaits each `poll` in sequence. After a hot reload `activePolls` is empty, so `/follow-team` on an existing 20-team list would await up to 20 sequential fetches before replying.
     - In normal sessions only one team is missing, so impact is low. Your ruling that session.start re-polls everything does not cover this.
     - Fix: reuse the stagger helper, or document the deviation.
  
  ### Minor
  3. **:578 and :581-583. A dead loop is possible.**
     - If `update` or `$.store` throws inside `poll`, `activePolls` keeps the key but no timer is set. `syncPolls` then never restarts that team.
     - Pre-existing in spirit (the stagger path's `.catch(() => {})` swallows it), but more visible with many teams.
  4. **:429-436. Row order and "first reading wins" follow `readings` insertion order, not follow order.**
     - Order is set by which poll finished first, and a team whose reading was deleted and re-added moves to the end.
     - Effects: a shared game's bold followed side depends on poll timing, and live rows (which have no tiebreak) can swap positions between polls.
     - The spec and the rules file both say "follow order". Sort by index in `followedTeams`, or soften the wording.
  5. **:588-591. `lastToast` is never pruned.** It grows by one entry per game for the life of the module. The growth is trivial, but it is a known unbounded map.
  6. **:270-276. `unfollow` always replies "Stopped following X", even if the team was already gone.** Only reachable in a race.
  7. **Hot reload.** Module maps reset but old timers are not cancelled, so loops can double until reload settles. This is the same pattern as the old single `pendingPoll`, so it is not a regression.
  8. **Repeated session.start.** Stagger timers from earlier calls still fire, causing extra fetches. They are harmless because the generation supersedes them.
